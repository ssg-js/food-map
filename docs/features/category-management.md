# Problem

기존 카테고리의 이름·분류 변경과 정리가 불가능했다.

# Why

잘못 입력한 이름과 기존 미분류 데이터를 실제 사용 중 정리할 수 있어야 한다.

# Decision

기존 ID와 맛집 관계를 유지해 이름·FOOD/PURPOSE 분류를 수정한다. 공용 데이터의 수정·삭제는 관리자 권한으로 제한한다.

# Implementation

- 웹 `/categories`, 앱 같은 경로에서 그룹과 연결된 맛집 개수 표시.
- 1~20자, 앞뒤·연속 공백 정규화, 동일 그룹 중복 거절.
- UNCLASSIFIED는 보존하여 표시하고 FOOD/PURPOSE로 재분류 가능.
- Category.updatedAt 추가 migration은 기존 데이터·관계를 삭제하지 않는다.
- 수정/삭제 시 expectedUpdatedAt 검사로 오래된 화면의 덮어쓰기 방지.
- 삭제 전 연결 개수와 해제 범위를 안내하고 확인. 카테고리를 삭제해도 맛집은 유지.

# Result

실제 연결된 테스트 맛집이 카테고리 삭제 후에도 남는지 API/DB로 검증했다. 웹/앱에서 이름·분류 변경을 검증했다.

# Retrospective

관리 권한은 개발용 접근 키를 사용한다. 운영 배포 전 개인 계정 기반 권한·감사 기록 체계가 별도로 필요하다.
