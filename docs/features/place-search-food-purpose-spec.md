# 맛집 검색과 사용자 카테고리 등록 · v3

작성일: 2026-11-09. 상태: 기능·디자인 검토안. 기존 v2 메인 화면은 사용자 요청으로 확정 보관한다. v3 시안 확정 및 신규 카테고리 분류 구현은 별도 단계다.

## 1. 문제와 목표

사용자가 Google에서 찾은 맛집을 음식 종류와 방문 목적에 따라 정리한다. 예를 들어 한 식당에 `양식`, `파스타`와 `데이트`, `푸드파이트`를 함께 연결할 수 있어야 한다.

기본 흐름: 장소 검색 → 후보 1곳 선택 → 음식 종류·방문 목적 선택 또는 생성 → 맛집 저장.

## 2. 조사 결과와 재사용 범위

- `prisma/schema.prisma`에 Restaurant, Category, RestaurantCategory 모델이 이미 있다.
- Restaurant에는 내부 ID, 고유 googlePlaceId, 생성·수정 시각만 있으며 Google의 이름·주소·좌표·사진·평점은 저장하지 않는다.
- `prisma/migrations/20260915000000_add_place_registration_categories/migration.sql`에 기존 구조의 마이그레이션이 있다. 이번에는 실행 중 DB의 적용 이력이나 실제 데이터를 조회하지 않았다.
- `GET /api/places/search?q=`가 Text Search (New)를 호출한다. 현재 FieldMask는 `places.id,places.displayName.text,places.formattedAddress`다.
- `GET/POST /api/categories`가 전역 공용 카테고리 조회·생성을 지원한다.
- `GET/POST /api/restaurants`가 Place ID 저장과 카테고리 연결을 지원한다. 같은 ID는 중복 생성하지 않으며 최종 카테고리 집합을 트랜잭션으로 반영한다.
- 웹·앱은 `packages/registration`의 API와 등록 로직을 공유한다.
- `.env`의 지도용 키, 서버 Places 키 및 검색 활성화 설정이 존재한다. 값은 문서에 복사하지 않았다. 키의 유효성·허용 API·실제 잔여 무료 사용량은 Cloud Console 또는 별도 연동 확인이 필요하다.

따라서 Place ID 저장용 백엔드나 테이블을 새로 만들지 않는다. 기존 모델을 재사용하고 카테고리의 분류 필드만 확장하는 안을 제안한다.

## 3. 용어와 데이터 정책

식당을 식별하는 값은 **Place ID**다. Google의 **Map ID**는 지도 설정·스타일 등에 쓰는 다른 식별자이므로 Restaurant 키로 사용하지 않는다.

- 영구 저장: Place ID, 서비스 자체 ID·시각, 사용자가 직접 만든 카테고리와 연결 관계.
- Google 장소 이름·주소는 현재 검색 결과를 표시하는 데 사용하며 DB·localStorage·AsyncStorage·서비스 워커·검색 로그에 영구 보관하지 않는다.
- 좌표 캐시를 새로 도입하지 않는다. 저장된 맛집 마커는 이번 범위에서 제외한다.
- Google 응답으로 음식 종류나 방문 목적을 자동 생성하지 않는다. 이 분류는 사용자 입력이다.
- 검색 응답의 서버/CDN 캐시를 `Cache-Control: no-store`로 명시하고 Google 요청도 `cache: no-store`로 지정하는 보완이 필요하다.
- 현재 검색 훅의 5분 재사용 캐시를 비용 절감의 일반적인 근거로 삼지 않는다. 후속 구현에서는 현재 화면 표시 상태만 유지하고 이탈 시 제거하며, 응답 저장·재사용 정책을 Google 약관에 맞춰 검토한다.
- 지도에 Google Places 결과를 표시한다면 Google 지도 위에 표시한다. Apple 지도에 Google 검색 결과 마커를 배치하지 않는다. 현재 네이티브 앱의 Apple 지도 기본값은 후속 마커 기능 전에 변경 또는 제거해야 한다.
- 지도 없이 검색 결과를 보여주는 경우에도 공식 Google Maps 출처 표기 규칙을 따른다. 시안의 글자는 배치 예시이며 구현 시 공식 로고·여백·대비 규칙을 적용한다.
- 공개 이용약관·개인정보처리방침에서 요구되는 Google 약관·정책 연결을 제공한다. 시안의 링크는 아직 구현된 페이지가 아니다.

이 문서는 정책에 맞춘 설계 방향이다. 현재 서비스 전체의 정책 준수 검증 완료를 뜻하지 않는다.

## 4. 무료 사용량과 호출 제한

2026-11-09 확인한 글로벌 종량제 가격표 기준:

- 웹 지도 Dynamic Maps: 월 10,000 과금 이벤트 무료. 이후 첫 구간은 1,000회당 USD 7.
- 현재 필드의 Text Search Pro: 월 5,000 과금 이벤트 무료. 이후 첫 구간은 1,000회당 USD 32.
- Text Search Essentials (IDs Only)는 무료 사용량이 Unlimited로 기재되어 있지만, 이름·주소를 함께 표시하는 현재 검색에는 적용되지 않는다.
- 네이티브 Maps SDK 지도 표시는 웹 Dynamic Maps와 별도 SKU다. Places 검색 과금은 별도로 남는다.

무료량은 사용자별 검색 횟수가 아니며 동일 결제 계정에 연결된 프로젝트 사용량을 함께 고려해야 한다. 무료량 초과 시 자동으로 검색이 중지되는 구조가 아니다. 가격표만으로 이 프로젝트의 잔여량을 계산할 수 없다.

호출 제어 요구사항:

1. 2자 이상 검색어를 입력하고 검색 버튼/Enter로 제출할 때만 Google 호출.
2. 입력 중 자동완성, 지도 이동·렌더·창 재포커스로 검색하지 않음.
3. 요청 중 중복 제출 차단, 자동 재시도 없음. 오류 후 사용자가 재시도.
4. 카테고리 생성·선택·맛집 저장에는 Google 요청 없음.
5. Cloud Console에서 API 제한과 제공되는 quota를 설정하고 예산 알림을 켠다. 예산 알림은 강제 지출 차단 장치가 아니다.
6. 운영 전 서버의 사용자/IP별 속도 제한과 공유 저장소 기반 일·월 호출 한도 도입을 별도 검토한다. 프로세스 메모리 카운터만으로 여러 서버의 한도를 보장하지 않는다.

현재 코드에는 전체 월 무료량을 보장하는 하드 제한이 없다. 이번 작업에서는 Google Cloud 설정을 변경하거나 유료 검색을 실행하지 않았다.

## 5. 기능 요구사항

### F-01 장소 검색

- 식당명 또는 지역+음식으로 검색한다. 예: `성수 파스타`.
- 결과는 이름·주소만 보여주며 한 장소만 선택한다.
- 최소 길이 미달, 검색 중, 결과 없음, 비활성, 외부 API 오류, 한도 초과를 구분한다.
- 실패 시 기존 입력을 유지하고 재시도를 제공한다.
- 이름/주소 검색은 Google Places 검색이며 서비스 카테고리 필터와 구분한다. 장소가 실제 맛집인지는 사용자가 판단한다.

### F-02 음식 종류

- 한식·일식·양식·파스타 등은 사용자 정의 값의 예시다. 고정된 Google 분류 목록으로 강제하지 않는다.
- 0개 이상 복수 선택 가능하다. 사용자에게 필수 선택을 강제하지 않는다.
- `+ 직접 추가`를 누르면 해당 그룹 안에 입력 폼을 연다.

### F-03 방문 목적

- 데이트·혼밥·친구 모임·푸드파이트·기념일 등을 사용자가 생성한다.
- 음식 종류와 독립적으로 0개 이상 복수 선택한다.
- 두 그룹 모두 동일한 선택·추가 컴포넌트 패턴을 사용한다.

### F-04 카테고리 생성

- 그룹은 사용자가 누른 추가 버튼으로 정해진다. 이름은 앞뒤 공백 제거 및 연속 공백 축약 후 1~20자.
- 같은 그룹 안의 같은 이름은 중복 생성하지 않고 기존 항목을 선택한다.
- 다른 그룹에서는 같은 이름을 허용한다.
- 생성 성공 시 해당 칩을 목록에 넣고 자동 선택한다. 실패 시 입력을 보존한다.
- 추가 전 입력한 이름은 아직 선택 수에 포함하지 않는다. 입력 중 저장하려 하면 먼저 추가 또는 취소하도록 안내한다.
- 이름 바꾸기·삭제·카테고리 관리자 화면은 이번 범위 밖이다.

### F-05 맛집 저장과 재편집

- 선택 장소의 Place ID와 두 그룹의 categoryIds 합집합만 서버로 보낸다.
- 서버가 categoryIds 존재 여부를 검증한다. 중복 ID는 제거하고 없는 ID가 있으면 전체 요청을 거절한다.
- 같은 장소는 기존 Restaurant를 재사용한다. categoryIds는 추가분이 아니라 최종 전체 집합이다.
- 이미 저장된 장소 선택 시 기존 카테고리 연결을 먼저 불러온 뒤 수정한다. 기존 연결을 모르고 덮어쓰는 동작을 방지한다. 현재 프론트에는 이 보완이 필요하다.
- 진행 중 이중 저장을 차단하고, 성공 후 완료 안내와 다음 장소 등록 동작을 제공한다.
- 저장 실패 시 장소·칩 선택을 유지한다. 오프라인 저장 대기열은 만들지 않는다.

### F-06 소유권의 현재 범위

현재 인증·소유자 모델이 없으므로 '사용자가 설정'은 사용자가 이름을 직접 입력할 수 있다는 뜻으로 해석한다. 카테고리와 맛집 관계는 서비스 공용이다. 사용자별 비공개 목록이나 개인 카테고리가 필요하면 인증·소유권 모델을 별도 승인받아 확장한다. 시안은 개인 전용 저장소가 이미 있다는 의미가 아니다.

## 6. DB·API 변경 제안 (미적용)

두 별도 카테고리 테이블보다 기존 Category에 분류 필드를 추가하는 방식이 기존 연결 테이블과 저장 API를 재사용하기 쉽다.

```prisma
enum CategoryKind {
  FOOD
  PURPOSE
  UNCLASSIFIED
}

// Category 모델 변경안의 주요 필드. 현재 실행 스키마가 아니다.
// name의 기존 @unique는 복합 고유 제약으로 대체한다.
// kind CategoryKind @default(UNCLASSIFIED)
// @@unique([kind, name])
```

- FOOD: 음식 종류. PURPOSE: 방문 목적.
- 기존 항목은 음식과 목적이 섞여 있으므로 일괄 FOOD 지정하지 않는다. UNCLASSIFIED로 보존하고 검토 후 분류한다.
- 기존 맛집 연결과 카테고리 ID는 유지한다. 기존 항목이 있으면 편집 화면의 `기존 카테고리 · 분류 전` 보조 영역에 표시하여 누락 저장을 방지한다.
- 새 생성 API는 FOOD 또는 PURPOSE만 허용한다. UNCLASSIFIED는 기존 데이터 이행용이다.
- GET categories 응답 항목: `{ id, name, kind }`.
- POST categories 요청: `{ name, kind: "FOOD" | "PURPOSE" }`; 성공 201, 입력 오류 400, 같은 그룹 중복 409.
- Restaurant 응답의 categories에도 kind를 포함한다.
- 기존 장소 편집을 위해 Place ID로 기존 연결을 조회하는 제한된 API 계약을 추가한다. 현재 200개 제한 전체 목록으로 존재 여부를 추정하지 않는다.
- 저장 요청 `{ googlePlaceId, categoryIds }`와 기존 트랜잭션은 유지한다.

영향 파일: `prisma/schema.prisma`, 새 migration, categories/restaurants API, 엔티티 타입, `packages/registration`, 웹 PlaceRegistrationPanel, 앱 RegistrationScreen, 테스트.

위험: 기존 클라이언트와 kind 필드 계약 불일치, 혼합 카테고리의 잘못된 자동 분류, 재편집 중 기존 연결 손실. 대응: 데이터 보존 migration, 두 클라이언트 동시 변경, 기존 관계를 포함한 통합 테스트. 실제 DB 적용 전 백업과 대상 DB 확인이 필요하다.

## 7. 디자인과 상호작용

- 기존 v2 웹·앱 메인은 `디자인/확정/{웹,앱}/01_맛집등록`에 원본 그대로 이동한다.
- 신규 v3는 `디자인/수정중/{웹,앱}/02_음식종류와방문목적`에서 검토한다.
- 웹: 왼쪽 검색/등록 패널, 오른쪽 지도. 음식 종류와 방문 목적을 연속 배치한다.
- 앱: 짧은 지도 위젯과 스크롤 가능한 등록 화면. 장소 선택 후 결과를 접어 카테고리 공간을 확보한다. 키보드가 열리면 입력 폼을 가리지 않게 이동한다.
- CategoryGroup(title, kind), CategoryChip, InlineCategoryCreate, SelectedPlace, SaveAction 패턴을 재사용한다. 웹과 네이티브는 렌더러를 분리하고 API·검증·선택 로직을 공유한다.
- 추가 폼은 한 번에 하나만 열고 취소 시 칩 선택을 유지한다. 저장 CTA는 하단 안전 영역과 키보드를 고려한다.
- 파랑 #3182F6, 본문 #191F28, 보조 #6B7684, 배경 #F2F4F6. 작은 글자 대비는 구현 단계에서 검증하고 필요하면 진한 파랑을 사용한다.
- 칩은 색상뿐 아니라 체크 표시와 접근성 선택 상태를 제공한다. 키보드 이동·포커스·화면낭독기·최소 44px 터치 영역을 검증한다.
- 시안의 장소와 지도는 가상 예시다. 공식 지도·출처 에셋을 대체하지 않는다.

## 8. 완료 기준과 검증 계획

1. 검색 버튼 1회에 외부 호출이 최대 1회 발생하며 칩 변경·저장에는 외부 호출이 없다.
2. 음식과 목적을 동시에 선택하고 각각 새 이름을 생성할 수 있다.
3. 그룹별 이름 중복과 공백 정규화를 검증한다.
4. 같은 Place ID 재저장 시 Restaurant는 1개이고 최종 관계가 정확하다.
5. 기존 미분류 카테고리와 연결이 migration 및 편집에서 보존된다.
6. Google 이름·주소 등이 DB나 영속 캐시에 남지 않는다.
7. 실패·오프라인·위치 권한 거부·검색 한도에서 UI가 복구 가능하다.
8. 웹/앱 공통 API 테스트, DB 트랜잭션 통합 테스트, 양쪽 화면 테스트, lint·typecheck·build를 실행한다. UI 테스트는 mock으로 유료 API 호출을 피한다.

이번 결과: 기존 코드/마이그레이션 및 설정 존재 확인, 공식 정책 조사, 기능명세와 웹·앱 정적 시안 작성, v2 확정 이동. 애플리케이션 코드·DB·배포 설정은 변경하지 않았다. 위 검증 항목은 후속 구현의 완료 기준이며 이번에 통과했다고 주장하지 않는다.
