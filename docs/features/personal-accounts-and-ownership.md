# Problem
공용 저장소와 관리자 접근 키는 개인 맛집 보관 서비스 요구와 맞지 않는다.
# Why
다른 계정의 자료가 조회되거나 연결되지 않아야 한다.
# Decision
직접 인증 구현과 인증 라이브러리를 비교하고 Better Auth + 기존 PostgreSQL/Prisma를 선택했다. 외부 인증 서비스 없이 아이디/비밀번호로 시작하고 OAuth는 추후 추가한다.
# Implementation
- `/setup`: 최초 설정 토큰으로 한 계정만 생성. 공개 가입 API 없음. 생성 중 PENDING 계정은 로그인 불가, 정상 완료 시 OPERATOR. 중복 요청은 CAS로 1건만 승인.
- `/login`, `/api/auth/{login,session,logout}`: 비밀번호 보안 해시, 8시간 서버 세션, 웹 HttpOnly 쿠키와 Origin 검증, 앱 Bearer + SecureStore. 비밀번호와 Google 내용은 디바이스에 저장하지 않음.
- 아이디당 15분 10회 실패 제한. 인증 비밀이 없으면 실패 처리. 내부 이메일 식별자는 전송되지 않음.
- 모든 개인 API ownerId 조건. Restaurant/Category/연결 테이블의 복합 FK로 다른 계정의 연결도 DB 차단.
- 기존 자료는 로그인 불가능한 격리 계정 아래 보존. 최초 설정의 가져오기 체크 시에만 기존 분류·맛집·연결을 한 트랜잭션으로 이동. 기본은 가져오지 않음.
- 기존 관리자 키 로그인 API는 410. 관리자 사용량 페이지는 개인 계정 OPERATOR만 접근.
- 웹 로그아웃은 캐시 삭제/전체 페이지 이동/다른 탭 알림. 앱은 암호화 토큰과 Query 캐시 삭제.
# Result
실제 DB와 서버로 소유권, CSRF, 웹 쿠키/앱 토큰, 로그아웃 폐기, 최초 설정 경쟁, 기존 자료 가져오기 검증.
# Retrospective
이메일 복구·비밀번호 찾기·공개 회원가입은 범위 밖이다. 비밀번호 복구 도구는 이번 승인 범위에서 제외했다. 다중 사용자 공개 전에는 계정 발급 정책, 로그인 IP 제한과 운영 모니터링을 별도 정의한다.
