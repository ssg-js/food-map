# Problem

등록한 맛집을 다시 보거나 음식·방문 목적에 맞게 좁혀볼 수 없었다.

# Why

등록 이후에도 실제로 사용할 수 있는 목록·지도·수정 흐름이 필요하다.

# Decision

기존 Place ID와 서비스 카테고리 구조를 유지한다. Google 이름·주소·좌표는 화면을 표시하는 동안만 조회하며 DB/영속 캐시에 복제하지 않는다. 웹과 앱이 같은 API를 사용한다.

# Implementation

- `/saved`: 12개 단위 목록, 페이지 이동, 음식 종류·방문 목적 필터와 초기화.
- 같은 분류의 여러 항목은 OR, 음식과 목적 그룹 사이는 AND.
- `/api/restaurants?page=1&food=...&purpose=...`: 전체 개수와 페이지 정보 포함.
- `/api/places/:placeId`: 최소 Place Details 정보와 출처. 서버 집계 후 호출, timeout, no-store, 화면 이탈 시 취소.
- 목록의 지도 보기: 선택 장소로 중심 이동 및 핀 갱신. 웹은 지도 인스턴스를 재사용한다.
- 정보가 사라진 장소도 등록 정보·카테고리를 남겨 수정/삭제가 가능하다.
- `/api/restaurants/:id` PATCH/DELETE: 관리자 세션/네이티브 서명 토큰과 수정 버전 검증. 충돌 409, 입력 오류 400, 권한 없음 401.
- 기존 등록 화면에서 재저장할 때도 수정 권한·버전을 검사해 우회를 막는다.
- 삭제 확인을 거친 뒤 연결만 정리하며 Google 장소나 카테고리 자체는 삭제하지 않는다.

# Result

실제 로컬 서버·분리 DB 브라우저 테스트에서 목록, 필터, 수정, 충돌 거절, 삭제와 권한 검사를 확인했다. Google 응답은 반복 검증에 한해 모킹한다.

# Retrospective

현재 서비스는 공용 목록이다. 개인별 비공개 목록/개인 계정/SSO/MFA는 별도 범위다. Place Details와 Text Search는 서로 다른 SKU이며 내부 카운터는 두 호출의 합을 보수적으로 기록한다. 개발 한도 해제는 유지한다. Maps JavaScript 지도 로드는 이 카운터와 별개다.
