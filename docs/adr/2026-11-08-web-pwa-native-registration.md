# Context

MVP 7은 장소 검색 → 후보 선택 → 자체 카테고리 선택·생성 → 등록이다. 기존 화면은 지도 위 절대 위치 패널 하나에 이 흐름이 집중되어 작은 화면과 데스크톱을 함께 다루기 어려웠다. 사용자는 v2 디자인을 기준으로 웹/PWA와 별도 Expo 앱의 개발을 요청했고, 이 구조에 동의했다. 배포는 범위 밖이다.

# Options

1. 웹을 WebView로 감싸기: 빠르지만 별도 네이티브 화면과 위치 UX가 없다.
2. 웹과 Expo 화면을 각각 만들고 API·등록 상태 처리를 공유하기: 플랫폼에 맞게 UI를 만들면서 동작 차이를 줄일 수 있다.
3. Next.js를 포함한 전체 저장소를 새 모노레포로 재구성하기: 이 작업의 UI 범위에 비해 영향이 크다.

# Decision

2번을 선택한다. 루트 Next.js 프로젝트와 기존 서버·Prisma 구조를 유지하고 `apps/mobile`에 독립 Expo 앱을 추가한다. 두 앱은 `file:` 의존성으로 `packages/registration`을 사용한다. 웹과 네이티브의 React 버전이 달라 별도 lockfile과 node_modules를 유지한다. 앱은 `.npmrc`의 `install-links=true`로 공통 패키지를 복사 설치해 상위 웹 프로젝트의 React가 따라오는 문제를 막는다. 시작과 export 전에 공통 소스를 자동 갱신하고 Metro 기본 설정을 사용한다. 공통 소스를 수정한 경우 앱 개발 서버를 다시 시작하면 반영된다.

- 공통 패키지: DTO 검증, 20초 요청 제한, 카테고리 이름 정규화, 검색/선택/생성/저장 컨트롤러.
- 웹: 기존 FSD 계층을 유지하고 widgets에서 화면을 조합한다.
- 네이티브: Expo Router + 플랫폼 UI. iOS는 Apple Maps 기본 공급자, Android는 별도 네이티브 지도 키가 있을 때만 실제 지도를 표시한다.
- 서버 API와 DB 스키마는 그대로다. CORS 변경 없이 네이티브 fetch로 기존 Route Handler를 사용한다.
- 검색은 명시적 제출만 사용하고 자동 재시도·포커스 재검색을 끈다. 5분 메모리 캐시를 사용하며 기기에 영구 저장하지 않는다.
- 카테고리·맛집 생성 중에는 선택 변경을 잠가 다른 후보에 늦은 응답이 적용되는 문제를 방지한다.
- PWA는 자체 오프라인 안내와 아이콘만 캐시한다. API와 Google 콘텐츠를 서비스 워커에 저장하지 않는다.

# Consequences

- UI는 플랫폼별로 따로 유지하지만 API 계약과 등록 상태 처리는 하나다.
- 기존 API 자격 증명은 서버에만 남고 앱에는 서버 주소와 플랫폼용 지도 키만 설정한다.
- 현재 인증 없는 공용 카테고리 모델을 유지한다. 등록은 즐겨찾기가 아니며 사진·평점·거리·리뷰·맛집 마커를 추가하지 않는다.
- 앱 API 주소는 실기기에서 접근 가능한 LAN 주소 또는 HTTPS 주소여야 한다. localhost는 해당 기기 자신이다.
- 새로운 서버·클라우드 서비스·배포를 도입하지 않는다. 네이티브 서명 빌드와 스토어 제출은 별도 범위다.
- 지원되는 Node 24를 `.nvmrc`에 명시한다. 기존 환경의 Node 23은 Expo 58 지원 범위 밖이다.

# Verification Plan

웹 lint/typecheck/build, 공통 API 단위 테스트, 브라우저에서 웹·모바일 등록 흐름과 PWA 오프라인 테스트, 앱 lint/typecheck 및 iOS/Android Metro export를 실행한다. 전체 Xcode/Android SDK가 없는 환경에서의 실행 한계는 완료 보고에 구분한다.
