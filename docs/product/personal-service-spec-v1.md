# 개인용 맛집 보관 지도 · 기능명세 v1

작성일: 2026-11-13
상태: **2026-11-14 개발 착수 승인. 구현·검증 결과는 `docs/00_project-management/2026-11-14-personal-service-handoff.md`에서 추적한다.**
대상: 웹·PWA·Expo 앱. 기존 기술 스택과 확정 디자인을 재사용한다.

## 0. 이 문서의 기준과 읽는 방법

가장 최신 요구사항은 2026-11-13 사용자 요청이다. 기존 MVP1~7, 공용 목록 기능과 2026-11-12 인수인계는 **현재 구현을 설명하는 이력**이며, 앞으로의 개인용 서비스 요구사항을 대신하지 않는다.

- **확정 요구**: 사용자가 명시한 목표와 작업 방식.
- **제안 기본값**: 세부 내용이 지정되지 않아 검토 가능한 형태로 정한 안. 사용자 피드백에 따라 바꾼다.
- **현재 구현**: 코드·문서를 읽어 확인한 상태. 새 요구의 구현 완료를 뜻하지 않는다.
- 본문 FR 번호와 완료 기준을 이후 작업·테스트·커밋에서 추적한다.

현재 방향 전환의 핵심은 **공용 목록을 개인 계정별 비공개 보관함으로 전환하는 것**이다. 현재의 관리자 키는 개인 계정 로그인이나 소유권 검증을 대신할 수 없다.

## 1. 서비스 목표

### 1.1 확정 요구

사용자가 가고 싶은 맛집을 직접 저장하고, **어떤 목적으로 / 어떤 종류의 음식인지 / 어떤 음식·메뉴로 기억하는지** 직접 만든 카테고리로 분류하여 지도와 목록에서 다시 찾는다.

대표 사용자 흐름:

> 로그인 → Google에서 새 맛집 검색 → 후보와 위치 확인 → 내 카테고리 지정 → 직접 저장 → 내 보관함에서 목적·종류·대표 메뉴로 검색 → 지도에서 확인 → 필요하면 수정·삭제.

### 1.2 두 검색을 구분한다 · 사용자 확인 반영

- **새 맛집 찾기**: Google 등 외부 장소 API에서 상호명·음식 종류·대표 메뉴를 검색어로 사용해 후보를 찾는다. 사용자가 저장하지 않으면 개인 보관함에 추가하지 않는다.
- **내 맛집 찾기**: 내가 저장한 맛집을 내 카테고리로 검색한다. 필터의 판정은 내 DB 데이터로 수행한다. 지도·이름·주소 표시를 위한 외부 조회는 별도로 집계한다.

**사용자 확인**: 음식 종류·대표 메뉴는 Google의 새 장소 검색에도 반영한다. 내 저장 목록 검색과 새 장소 검색을 모두 지원한다. 다만 내 카테고리를 Google 전체 장소의 자체 분류 데이터로 간주하지 않으며, 방문 목적은 저장·내 보관함 분류로 사용한다. Google Places의 장소 검색을 활용하는 범위이며 길찾기 등 Google Maps의 모든 기능을 복제하는 뜻은 아니다.

### 1.3 사용 예시

- 방문 목적: `데이트`, `혼밥`, `부모님 식사`, `푸드파이트`.
- 음식 종류: `한식`, `일식`, `양식`, `중식`.
- 대표 음식·메뉴: `평양냉면`, `돈카츠`, `쌀국수`, `스테이크`.
- `데이트 + 일식 + 돈카츠`를 선택하면 세 조건을 만족하는 **내 저장 맛집**을 보여준다.
- ‘대표 음식’은 내가 기억하려고 붙인 분류다. 객관적인 인기·검증된 유명 메뉴라는 주장을 만들지 않는다.

## 2. 범위

### 2.1 이번 개인용 v1에 포함

- 계정 로그인·로그아웃·세션 및 계정별 데이터 격리.
- 외부 장소 검색·선택·지도 표시·사용자의 명시적 저장.
- 세 카테고리 그룹의 사용자 정의 값 생성·복수 선택·검색·수정·삭제.
- 내 저장 목록·지도·페이징·선택 장소 정보·현재 위치.
- 내 맛집 분류 수정·저장 해제와 동시 수정 충돌 방지.
- 외부 API 사용량 집계·일/월 총량 제한·상태 안내.
- 키 없이 동작하는 외부 API mock과 계약·오류·화면 테스트.
- 개인 서비스 운영에 필요한 최소 사용량 관리자 화면.
- 신규 페이지 디자인·문서화와 기능 단위 Git 이력.

기존 PWA와 웹·앱의 동작은 유지·재사용한다. 아래 제외 목록은 기존 유효 기능을 임의로 제거하라는 뜻이 아니다.

### 2.2 추후 확장으로 보류

- 일반 사용자 공개 모집과 공개 회원가입, 다수 사용자 운영 정책.
- 내 카테고리·보관함 공유, 공유 링크, 공개 프로필.
- 여러 사람의 공동 편집·추천.

공개 다중 사용자 운영을 미루더라도 **계정 소유권과 다른 계정 차단은 이번 v1의 필수 기능**이다. 테스트 계정 A/B로 이를 증명한다.

### 2.3 별도 요구 전에는 만들지 않음

- 리뷰·평점 작성, SNS·팔로우·좋아요·채팅.
- AI 추천·메뉴 자동 추출·유명도 판정·카테고리 자동 분류.
- 예약·주문·결제·구독·광고·사업자 관리.
- 길찾기·최적 동선·방문 인증·백그라운드 위치 추적.
- 사진·리뷰 대량 수집, 장소 자동 저장·전체 자동 동기화.
- 음식 가격·영업시간 등 별도 상세 데이터 수집.
- 새 인프라·과금 계정 연결·스토어 제출·실제 배포.

새 요구가 생기면 이 문서에 추가하고 작업 범위로 편입한다. 범위를 넓히기 위해 위 기능을 선제적으로 만들지 않는다.

## 3. 계정·권한

### FR-AUTH-01 로그인과 계정 생성 경로

**확정 요구**: 개인 계정으로 로그인해야 내 맛집에 접근할 수 있다.

**제안 기본값**:

- 사용자 확인: 본인의 계정을 만들고 아이디·비밀번호로 로그인한다. 이메일을 필수 로그인 식별자로 요구하지 않는다.
- 공개 회원가입은 누구나 새 계정을 만드는 기능을 의미한다. v1은 불특정 사용자 가입을 열지 않고 본인 계정을 생성한다. 초기 계정 생성 UI 또는 로컬 도구 중 구체적인 수단은 설계 단계에서 정하되 타인의 무단 계정 생성을 허용하지 않는다.
- 키나 외부 인증 서비스 연결 없이 검증할 수 있는 아이디/비밀번호 로그인부터 구현한다. 검증된 인증 라이브러리·비밀번호 보안 해시를 사용하며, 임의 암호화나 평문 비밀번호 저장은 금지한다.
- OAuth 로그인은 추후 추가·전환할 수 있도록 인증 수단과 내부 계정 ID를 분리한다. 전환하더라도 기존 맛집·카테고리의 소유권을 보존한다. 아이디/비밀번호 로그인과 OAuth의 실제 병행·전환 정책은 추후 결정한다.
- A/B 계정은 개발·테스트 도구로 만들 수 있어야 한다.
- 비밀번호 찾기용 외부 메일 발송은 이번 범위에서 제외한다. 개인 계정 복구는 로컬 운영 절차로 제공한다.
- 로그인 실패는 계정 존재 여부를 노출하지 않는 안내를 사용하고 반복 시도를 제한한다.

**완료 기준**:

- 올바른 자격 증명으로 웹·앱에서 로그인하고 잘못된 자격 증명은 거절한다.
- 로그아웃·세션 만료·폐기 후 보호 API를 사용할 수 없다.
- 비밀번호·토큰을 Git, 로그, 화면 오류, URL에 남기지 않는다.
- 인증은 mock 처리하지 않고 실제 세션과 테스트 DB로 검증한다.

### FR-AUTH-02 세션과 화면 보호

- 미로그인 상태는 로그인 화면을 표시한다. API는 HTML 리다이렉트 대신 401을 반환한다.
- 웹은 HttpOnly·SameSite와 운영 HTTPS의 Secure 쿠키를 사용한다.
- 앱의 장기 로그인 보관이 필요하면 OS 보안 저장소를 사용한다. 기본 저장 방식과 세션 기간은 구현 설계에 기록한다. 초안 기본 세션 기간은 8시간이며 ‘로그인 유지’ 옵션은 제외한다.
- 로그인 후 복귀 주소는 서비스 내부의 허용 경로만 받는다.
- 로그아웃·사용자 변경 시 개인 데이터 쿼리·선택 장소·필터·토큰을 정리한다. 브라우저 뒤로 가기로 이전 사용자의 개인 정보가 그대로 노출되어서는 안 된다.
- 개인 데이터 쿼리 키에 계정 식별자를 포함하고 계정 사이 캐시를 공유하지 않는다.

### FR-AUTH-03 소유권과 계정 격리

- 사용자 소유 맛집·카테고리·연결 관계의 모든 조회·생성·수정·삭제에서 서버가 세션의 userId를 기준으로 검사한다.
- 요청 body/query의 ownerId/userId를 믿거나 클라이언트의 버튼 숨김만으로 권한을 판단하지 않는다.
- A가 B의 맛집·카테고리 ID, 수정 버전, URL을 알아도 조회·연결·변경·삭제하지 못한다.
- 다른 계정 소유 객체는 존재 여부를 노출하지 않는 404를 기본값으로 사용한다. 미로그인은 401이다.
- 목록 개수·카테고리 연결 개수·검색 결과·페이지 수에도 다른 계정 데이터가 섞이지 않는다.
- 관리 역할이 있다는 이유로 다른 계정의 개인 보관함에 접근하는 우회 경로를 만들지 않는다. 운영 관리자는 필요 최소한의 API 사용량을 본다.
- 기존 관리자 키·쿠키가 새 개인 데이터 보호 규칙을 우회하지 못해야 한다.

**필수 계정 격리 시나리오**:

1. A/B가 같은 Google 장소를 각각 저장할 수 있고 서로의 분류는 보이지 않는다.
2. A/B가 같은 이름의 카테고리를 독립적으로 만들 수 있다.
3. A가 B의 카테고리 ID를 자기 맛집 저장 요청에 넣으면 요청 전체가 거절되고 기존 관계는 보존된다.
4. A가 B의 ID로 직접 API를 호출하거나 쿼리를 조작해도 응답 본문·개수·오류에서 개인 정보가 새지 않는다.
5. A 로그아웃 후 B 로그인 시 A의 화면 캐시가 남지 않는다.

## 4. 외부 맛집 검색과 저장

### FR-SEARCH-01 새 맛집 검색

- Google Places를 초기 제공자로 사용한다. UI는 우리 DTO만 받고 제공자별 응답 변환은 서버 어댑터에서 수행한다.
- 로그인한 사용자가 상호명·지역·음식 종류·대표 메뉴를 자유 입력하거나 음식 종류·대표 메뉴를 선택해 검색어에 반영한 뒤 검색 버튼 또는 Enter로 제출한다. 기존 최소 길이 정책을 재사용하여 최종 검색어는 2~200자로 제안한다.
- 예: `성수 돈카츠`, `강남 일식 스시`, 특정 상호명. 음식 종류·메뉴만으로도 검색할 수 있고 상호명 입력은 필수가 아니다.
- 선택한 음식 종류·메뉴는 최종 검색어에 합쳐 Google Places의 지원 검색 옵션으로 전달한다. 전송할 검색어가 화면에서 확인 가능해야 한다. Google이 지원하는 음식점 유형 조건을 활용하되 사용자 정의 문자열을 임의의 Google 유형 코드로 보내지 않는다.
- Google의 검색 결과·관련성 판단을 활용한다. 앱이 임의의 인기 메뉴·추천 결과를 생성하지 않는다. 위치·유형 등 구체 옵션은 공식 API 계약을 확인하여 문서화한다.
- Google 검색용 음식/메뉴 선택과 저장할 카테고리 연결은 별도 동작이다. 검색했다고 카테고리를 자동 생성·저장하거나 맛집을 저장하지 않는다. 저장 전에 사용자가 연결할 분류를 확인한다.
- 입력 중 자동 검색, 지도 이동에 따른 자동 검색, 창 재포커스·재렌더에 따른 자동 재호출은 하지 않는다.
- 진행 중 같은 요청을 중복 제출하지 않는다. 자동 재시도는 기본적으로 사용하지 않는다.
- 결과에 이름·주소·선택 상태·필요한 출처를 표시한다. 사진·평점·리뷰는 추가하지 않는다.
- 결과 중 한 곳을 선택하면 해당 위치와 선택 장소 정보를 표시한다. 선택은 저장이 아니다.
- 결과 없음·네트워크 오류·키 없음·제공자 오류·한도 초과를 구분해서 안내한다.
- API 키는 서버 전용 Places 키와 공개 지도 키를 구분한다. 서버 키를 웹·앱 번들에 넣지 않는다.

**완료 기준**: 검색 동작 1회에 필요한 외부 검색 요청만 발생하고 카테고리 선택·생성·저장 동작은 외부 검색을 호출하지 않는다. 실패 후 입력과 재시도 경로를 보존한다.

### FR-SAVE-01 내 보관함에 저장

- 사용자가 ‘내 맛집에 저장’을 눌러야 저장한다. 자동·백그라운드 저장은 하지 않는다.
- 필수값은 선택한 장소의 제공자 식별자와 **방문 목적·음식 종류·대표 메뉴 세 그룹 중 하나 이상에서 선택한 카테고리 1개 이상**이다. 세 그룹을 모두 채울 필요는 없다.
- 예: 방문 목적 `데이트`만 있어도 저장 가능. 음식 종류 `한식`만, 대표 메뉴 `평양냉면`만 선택해도 저장 가능. 아무 항목도 없으면 저장하지 않는다.
- 저장 버튼 상태와 입력 안내뿐 아니라 서버에서도 최소 1개 규칙을 검사한다. 다른 계정 항목이나 미분류 항목만 전송해 조건을 우회할 수 없어야 한다.
- 같은 계정·같은 제공자·같은 Place ID의 중복 저장은 막는다.
- 이미 내 보관함에 있으면 ‘저장됨’과 수정 동작을 제공한다. 새 레코드로 중복 추가하지 않는다.
- 저장 성공·진행·실패를 표시하고 이중 제출을 차단한다. 실패 시 선택을 유지한다.
- 카테고리 생성과 맛집 저장은 구분한다. 카테고리를 만들었다고 장소까지 자동 저장하지 않는다.
- 다른 계정의 동일 장소 저장 여부는 알려주지 않는다.

## 5. 개인 카테고리

### FR-CAT-01 세 그룹과 직접 정의한 값

**제안 기본값**: 그룹은 우선 세 개로 고정하고 그룹 안의 값은 사용자가 직접 정의한다.

- `PURPOSE` 방문 목적: 데이트, 혼밥 등.
- `FOOD` 음식 종류: 한식, 일식 등. 기존 enum을 재사용한다.
- `DISH` 대표 음식·메뉴: 평양냉면, 돈카츠 등. 신규 그룹이다.
- 각 그룹 자체는 비워둘 수 있고 복수 선택할 수 있다. 단, 저장한 맛집에는 세 정상 그룹을 통틀어 최소 1개 카테고리가 있어야 한다.
- Google 결과나 AI에서 분류를 자동 생성하지 않는다.
- 서로 다른 그룹에서 같은 이름을 허용한다. 사용자가 ‘파스타’를 음식 종류와 대표 메뉴 중 어디에 둘지 선택할 수 있다.
- 그룹 자체 추가·이름 변경 기능은 이번 범위에서 제외한다. 필요하면 다음 피드백에서 추가한다.

### FR-CAT-02 생성·변경·삭제

- 이름은 앞뒤 공백 제거와 연속 공백 축약 후 1~20자.
- 같은 계정·같은 그룹·같은 정규화 이름은 중복 생성하지 않는다. 같은 이름의 기존 내 항목을 선택할 수 있게 한다.
- 입력값을 아직 추가하지 않은 상태에서는 저장 전에 추가 또는 취소를 안내한다.
- 이름·그룹을 바꿔도 내 맛집의 연결 관계는 유지된다.
- 카테고리 삭제 전 **내 맛집 중 몇 곳의 연결이 해제되는지** 표시하고 확인한다. 삭제해도 맛집은 남는다.
- 제안 안전 정책: 삭제로 어떤 맛집의 마지막 정상 분류까지 없어지면 즉시 삭제하지 않고 영향 개수를 안내한다. 해당 맛집에 다른 분류를 먼저 연결하도록 하며 서버에서도 409로 차단한다. 최소 1개 규칙과 삭제 규칙을 트랜잭션으로 함께 보장한다.
- 다른 계정의 동일 이름 카테고리와 관계에는 영향이 없어야 한다.
- 기존 `UNCLASSIFIED`와 혼합 항목은 보존하고 직접 재분류한다. 기존 ‘파스타’ 등을 임의로 새 DISH 그룹으로 옮기지 않는다.

**완료 기준**: A/B 동일 이름 허용, 자기 그룹 내 중복 차단, 연결 유지 수정, 맛집 보존 삭제, 다른 계정 영향 없음, 버전 충돌 처리를 실제 DB로 검증한다.

## 6. 내 맛집 검색·목록·지도

### FR-FIND-01 내 카테고리로 찾기

- 로그인한 계정의 저장 맛집만 검색한다.
- 방문 목적·음식 종류·대표 메뉴 칩을 함께 선택할 수 있다.
- 같은 그룹의 여러 항목은 OR, 서로 다른 그룹은 AND로 결합한다.
- 예: `데이트 또는 혼밥` AND `일식` AND `돈카츠 또는 라멘`.
- 아무것도 선택하지 않으면 내 전체 저장 목록을 보여준다.
- 카테고리 이름을 텍스트로 찾아 선택하는 기능을 제공한다. 초안은 정규화된 이름의 부분 일치이며 유사어·오타 보정은 제외한다.
- 필터 변경·초기화 시 목록·개수·지도·페이지를 함께 갱신한다.
- 타인 카테고리 ID를 필터로 전달해도 그 데이터나 존재 여부를 노출하지 않는다.

### FR-LIST-01 내 저장 목록

- 최근 저장 순을 기본값으로 제안하고, 12개 단위 페이징을 기존 구현에서 재사용한다.
- 전체 개수와 현재 페이지가 모두 내 데이터 기준이어야 한다.
- 표시용 Google 정보는 현재 필요한 항목만 조회한다. 전체 보관함을 일괄 조회·동기화하지 않는다.
- 장소가 폐업·변경되거나 Google 정보를 가져오지 못해도 내 저장 관계와 분류는 보존한다. 상태 안내와 내 데이터 수정·삭제를 제공한다.
- 결과 없음과 로딩·실패·정보 일부 없음 상태를 구분한다.
- 마지막 페이지의 마지막 항목 삭제 시 유효한 페이지로 돌아간다.

### FR-MAP-01 지도와 선택 상태

- 목록과 동일한 검색 조건의 **현재 페이지에 포함된, 좌표를 확인한 내 맛집**을 핀으로 표시하는 것을 v1 기본값으로 제안한다.
- 전체 보관함이 지도에 전부 표시된 것처럼 보이지 않게 현재 페이지/표시 범위를 명시한다.
- 목록 클릭과 핀 클릭이 같은 선택 장소와 정보 패널을 가리킨다.
- 선택 장소로 중심을 이동하고, 페이지·필터에서 빠진 장소의 오래된 핀·정보 패널은 정리한다.
- 좌표가 없는 곳에 임의 좌표로 핀을 만들지 않는다.
- 현재 위치는 사용자가 버튼을 눌렀을 때만 권한을 요청한다. 실패·거부 시 기본 지도와 검색은 계속 사용할 수 있다.
- 현재 위치를 내 보관 데이터나 로그에 영구 보관하지 않고 백그라운드 추적하지 않는다.
- Google 장소 정보를 지도 위에 표시할 때 Google 지도를 사용하고 요구되는 출처를 유지한다.
- 웹과 앱은 같은 필터·선택·분류 의미를 사용한다. 앱은 현재 내부 지도 구현을 재사용할 수 있다.

**확인 필요**: 지도에 ‘현재 페이지’가 아닌 전체 검색 결과의 핀을 표시하려면 외부 호출량·표시 범위를 포함한 별도 정책이 필요하다. 초안에서는 전체 일괄 조회를 하지 않는다.

### FR-EDIT-01 내 맛집 수정·삭제

- 일반 사용자는 자신의 맛집과 카테고리를 수정한다. 개인 데이터 수정에 별도의 운영 관리자 키를 요구하지 않는다.
- 수정 시 현재 연결을 먼저 불러오고, 최종 선택 집합을 한 트랜잭션으로 반영한다. 수정 후에도 세 정상 그룹 중 최소 1개 분류가 있어야 한다. 마지막 분류를 해제하면 안내하고 저장을 막는다.
- 오래된 화면에서 다른 수정 내용을 덮어쓰지 않게 버전을 검증한다. 충돌 시 409와 새로고침/다시 선택 동작을 제공한다.
- 삭제 확인 후 내 저장과 연결만 제거한다. 다른 계정의 같은 장소, 다른 내 카테고리, Google 원본 장소는 남긴다.
- 오프라인 저장 큐·자동 재전송은 이번 범위에서 제외한다.

## 7. 외부 API 모드와 총 조회 제한

### FR-EXT-01 키 없이 개발 가능한 mock 모드

**확정 요구**: 새 외부 서비스를 조사하고 요청·응답 계약에 맞춰 구현하되, 키와 유료 계정 연결 없이 나머지 개발을 완료한다.

- 신규 개발·자동 검증의 기본값은 명시적인 `mock` 모드로 제안한다.
- 장소 검색·상세·지도 SDK까지 외부 네트워크 요청 없이 검증할 수 있어야 한다. 테스트 데이터라는 표시를 남긴다.
- 기존 로컬 키가 있더라도 새 개발에서 자동으로 실연동하거나 유료 호출을 실행하지 않는다.
- 실제 모드에서 키가 없거나 잘못되면 ‘연결 설정 필요’ 상태를 표시한다. 실패를 숨기고 mock 결과로 바꾸지 않는다.
- 환경변수 예제·설정 위치·필요 권한·콜백/허용 주소를 문서화한다. 비밀 값은 문서·커밋에 넣지 않는다.
- 제공자 공식 문서의 요청·응답 예시를 기반으로 DTO 변환과 mock fixture를 유지한다. fixtures는 가상 데이터이며 실제 개인정보를 복제하지 않는다.
- 정상, 결과 없음, 일부 필드 누락, 잘못된 JSON, 401/403, 404, 429, 5xx, 지연·취소를 테스트한다.
- 외부 키 대기 중에도 UI·DB·인증·소유권·한도·오류 처리는 끝낸다. 완료 보고에서 ‘mock 검증 완료’와 ‘실연동 미검증’을 구분한다.

### FR-LIMIT-01 호출 집계와 차단

- 검색 버튼 클릭 수와 실제 제공자 요청 수를 혼동하지 않는다. 상한은 **실제 외부 요청 전** 예약한 호출을 기준으로 한다.
- 검색과 Place Details를 모두 포함하되 제공자·API/SKU·환경별로 구분하여 기록한다.
- 계정별 제한과 프로젝트 전체 총량 제한을 함께 검사한다. 단일 개인 사용 단계에서는 전체 총량이 최종 안전장치다.
- 여러 서버·동시 요청·재시작에서도 상한을 넘지 않게 DB 기반 원자적 예약을 사용한다.
- 한도 미설정·DB 장애·검증 실패 시 실제 외부 호출을 보내지 않는다.
- 오류·취소·타임아웃은 보수적으로 예약량을 돌려주지 않는 안을 기본값으로 한다. 자동 재시도는 하지 않는다.
- mock 호출량은 실제 사용량과 별도 집계한다. 가짜 사용량 때문에 실제 잔여량이 바뀌어서는 안 된다.
- 초안 숫자 제안은 이전 설정을 재사용한 **일 100회·월 4,500회**다. 최종값은 검토 후 확정한다. 무료량을 보장하는 숫자로 취급하지 않는다.
- Google 일/월 구간은 미국 태평양 시간 기준으로 계산하고 화면에 기준을 명시한다. 새 월의 실제 사용량 전제가 불명확하면 확인 전 차단하는 기존 안전 정책을 재사용한다.
- 현재 코드의 개발용 실제 호출 차단 해제는 과거 설정이다. 새 개인용 개발은 mock을 기본으로 하고, 실제 연결 시 한도 검사를 필수로 제안한다. 전역 우회가 실연동에 조용히 남지 않게 한다.

### FR-LIMIT-02 지도 로드와 안내

- Places 호출 제한이 브라우저 Maps JavaScript 로드·공유 결제 계정의 다른 호출까지 제한한다고 주장하지 않는다.
- 실제 지도 로드도 운영 시 별도 통제 대상이다. 모드별 SDK 로드와 인스턴스 재사용, 지원되는 Google Cloud quota 설정 절차를 문서화한다.
- 해당 키로 직접 요청할 수 있는 범위는 앱 카운터만으로 보호되지 않으므로 실제 연결 때 제공자 키/API/웹사이트 제한을 별도로 적용한다.
- 한도 차단은 429와 식별 가능한 오류 코드를 반환한다. 프론트는 오늘/이번 달 제한과 재이용 가능 기준을 안내한다.
- 정보 조회가 차단되어도 이미 저장한 내 분류를 잃지 않고 관리할 수 있어야 한다.
- 외부 API에 의존하는 표시를 얻지 못하면 그 상태를 안내한다. 빈 지도·가짜 장소·무한 로딩으로 감추지 않는다.

### FR-OPS-01 최소 운영 관리자

- 운영 관리자만 실제/모의 환경, API별 호출 수, 일·월 설정 한도, 차단 상태와 기준 시간을 본다.
- 일반 사용자에게 다른 계정의 호출 수·맛집·카테고리를 노출하지 않는다.
- 기존 사용량 화면을 재사용하되 개인 계정 인증과 운영 역할을 구분한다.
- Google Monitoring 연결은 이번 범위에서 보류한다. 내부 집계를 Google 청구 금액·공식 무료 잔여량으로 표시하지 않는다.
- 한도 숫자의 화면 편집은 별도 요구 전에는 제외하고 서버 설정으로 관리한다.

## 8. 데이터·API 설계 요구

아래는 구현을 위한 모델 제안이며 이 문서 작성으로 스키마를 변경하지 않는다.

- `User`: 내부 계정 ID, 로그인 식별자, 인증 정보/라이브러리 참조, 역할과 시각.
- `Session`: 라이브러리가 관리하는 세션·만료·폐기 정보.
- `SavedPlace` 또는 기존 Restaurant 확장: 내부 ID, ownerId, provider, providerPlaceId, 수정 버전, 생성·수정 시각. 계정+제공자+장소 ID 복합 고유 제약.
- `Category`: 내부 ID, ownerId, FOOD/PURPOSE/DISH/기존 UNCLASSIFIED, 정규화 이름, 수정 버전, 시각. 계정+그룹+이름 복합 고유 제약.
- 연결 테이블: ownerId와 양쪽 객체를 참조하여 계정 간 교차 연결을 DB 제약 또는 동등한 강도로 차단한다.
- 사용량 테이블: 실제/모의 환경, 제공자·API, 기간·계정/전체 범위, 예약량·설정 한도. 장소 응답 본문이나 검색어를 집계 로그에 복사하지 않는다.

Google에서 가져온 이름·주소·사진·평점·리뷰를 개인 보관 데이터로 영구 복제하지 않는다. Place ID와 사용자가 직접 만든 분류를 저장하는 기존 방향을 유지한다. 좌표는 v1에서 영구 보관하지 않고 화면 표시용 일시 정보로 다룬다. 다른 캐시가 필요하면 해당 제공자·API의 현재 허용 범위를 먼저 확인하고 별도 ADR을 작성한다.

핵심 API 의미:

- 로그인/로그아웃/내 세션 확인.
- 로그인한 사용자 전용 장소 후보 검색·표시 정보 조회.
- 내 저장 목록의 페이징·카테고리 검색, 저장·수정·삭제.
- 내 카테고리 조회·생성·수정·삭제.
- 운영 역할 전용 사용량 조회.

기존 경로를 우선 재사용한다. 모든 보호 API는 인증 후 소유권 범위를 적용하고 `no-store` 등 개인 데이터 응답 정책을 일관되게 사용한다. 400 입력 오류, 401 미인증, 404 소유 객체 없음, 409 충돌/중복, 429 한도, 5xx 일시 장애를 UI와 함께 정의한다.

## 9. 기존 구현과의 차이·데이터 이행

### 재사용할 수 있는 부분

- Next.js/Expo, 공통 등록 로직, Google 어댑터와 지도 provider.
- 저장·카테고리 트랜잭션, 페이징, 두 그룹 필터, 수정 버전 검사.
- 서버 호출 예약, 오류 팝업, 사용량 대시보드.
- 웹/PWA·앱 디자인 토큰과 컴포넌트.
- 테스트 DB 분리, mock 외부 응답, 브라우저·번들 검증 도구.

### 신규 또는 변경 필요

- User/Session과 로그인 화면·앱 보안 토큰 처리.
- 현재 전역 Restaurant·Category와 고유 제약을 계정 범위로 변경.
- 현재 공개 조회/신규 등록 API를 인증·소유권 보호 대상으로 변경.
- ‘공용 데이터 관리용 관리자 키’ 요구를 ‘본인 데이터는 본인 세션으로 관리’로 전환.
- 대표 메뉴 DISH 그룹과 세 그룹 검색.
- 목록과 선택 핀 중심인 현재 지도에서 현재 페이지의 복수 핀과 선택 동기화.
- 실연동 중심 개발 설정을 명시적 mock 기본값과 실연동 필수 한도 정책으로 분리.

### 이행 원칙

- 기존 사용자의 맛집·카테고리·연결을 삭제하거나 임의로 다른 계정에 배정하지 않는다.
- 초기 소유자 계정이 확정되면 대상과 개수를 dry-run으로 확인하고 백업·복구 절차와 함께 이관한다.
- 소유자가 확정되지 않은 기존 데이터는 일단 비공개 격리하고 자동 공개하지 않는다.
- 기존 동일 장소/이름은 계정별 고유 제약으로 전환한다.
- FOOD/PURPOSE/UNCLASSIFIED를 보존하며 DISH 분류를 자동 추측하지 않는다. 기존에 정상 분류가 하나도 없는 저장 항목은 삭제하지 않고 ‘분류 필요’로 유지한다. 새로 저장하거나 기존 항목을 수정 저장할 때는 정상 분류 최소 1개를 요구한다.
- migration 검증은 별도 DB에서 먼저 수행한다. 실제 기존 데이터의 파괴적 정리·삭제는 별도 승인을 받는다.

## 10. 화면과 디자인 선행 절차

화면 제안: 로그인, 내 지도/보관함, 새 맛집 검색·저장, 카테고리 관리, 최소 운영 관리자. 독립 페이지/시트 구분은 기존 레이아웃을 검토해 디자인 단계에서 정한다.

새 페이지 또는 큰 화면 구조 변경은 다음 순서를 지킨다.

1. 페이지 목적·사용자 흐름·입력값·완료/오류/빈 상태를 문서화한다.
2. `디자인/수정중/{웹,앱}/페이지명/`에 시안과 설명·변경 이력을 저장한다.
3. 기존 공통 컴포넌트와 색·간격·모서리·타이포그래피 토큰 재사용을 정한다.
4. 디자인과 문서를 기준으로 기능을 구현한다. 이후 실제 화면 캡처를 남긴다.
5. 사용자가 확정한 디자인만 `디자인/확정/`으로 옮긴다. 이미지는 중복 복사하지 않고 검증 파일을 참조할 수 있다.

이 명세와 개발 착수를 승인한 뒤에는 페이지마다 다시 승인을 요청하지 않고 위 순서로 진행한다. 사용자는 결과물을 보고 수정할 수 있다. 시안은 구현 전 저장하되 스스로 사용자 승인 상태로 표시하지 않는다.

접근성·반응형 요구: 키보드 이동, 보이는 포커스, 라벨과 오류 연결, 칩 선택 상태, 최소 44px 터치 영역, 모바일 키보드/안전 영역, 가로 넘침 방지, 삭제 확인과 포커스 복귀.

## 11. 개발 단위와 진행 순서 제안

기존 구현을 전부 다시 만들지 않고 아래 작은 작업을 순서대로 진행한다. 한 단계 안에서도 독립적으로 검증 가능한 커밋으로 나눈다.

1. **개발 모드·외부 계약 정리**: mock 기본값, 네트워크 차단 테스트, fixture와 키 없는 실행 안내.
2. **로그인 디자인·실제 세션**: 초기 계정 도구, 웹/앱 로그인·로그아웃, 세션 만료.
3. **개인 소유권·데이터 이행**: owner 모델·고유 제약, 기존 데이터 이관 절차, A/B 계정 격리.
4. **개인 검색·저장 전환**: 모든 기존 API 인증·소유권 적용, 명시적 저장과 내 중복 방지.
5. **대표 메뉴 분류**: DISH 추가, 세 그룹 생성·변경·삭제와 기존 분류 보존.
6. **내 카테고리 검색·보관함**: 세 그룹 필터·이름 찾기·목록·페이징·수정·삭제.
7. **지도와 목록 동기화**: 현재 페이지 복수 핀, 선택·위치·상태 처리, 웹/앱 일치.
8. **실제 연결 준비·총량 제한**: 제공자/API별 집계, 계정/전체 상한, 실제 모드 필수 차단, 안내와 운영 화면.
9. **통합 회귀·인수인계**: 실제 서버와 분리 DB, 계정 격리, mock 지도/검색 오류, 빌드·사용 안내.

각 단계에서 디자인 필요한 부분은 구현 전에 저장한다. 인증·소유권 보호가 끝나기 전의 임시 상태를 개인 서비스의 완료본으로 보고하지 않는다.

## 12. Git·자율 진행·승인 범위

사용자가 명시한 개발 방식:

- 작은 기능별 브랜치 생성·코드 수정·로컬 테스트·커밋·작업 브랜치 푸시를 진행한다.
- 제목만 읽어도 작업을 알 수 있게 작성한다. 예: `feat(auth): 개인 계정 로그인과 로그아웃 구현`, `fix(saved): 다른 계정의 맛집 접근 차단`.
- 커밋 본문 또는 기능 문서에 관련 FR 번호, 디자인 문서, 검증 명령·결과·남은 한계를 기록한다.
- 최신 검증 완료 작업 브랜치를 기준으로 다음 기능 브랜치를 만들고 기준/의존 관계를 남긴다. main에 직접 작업하거나 자동 병합하지 않는다.
- 기능 완료 후 다음 승인된 미완료 기능으로 이어간다. 사용자가 중단하면 현재 상태·진행 중 프로세스·미완료 항목을 기록한다.
- 키가 없으면 mock으로 가능한 작업을 계속한다. 실제 연결만 ‘설정 대기/미검증’으로 남긴다.
- 배포, main 병합, 과금 계정/실제 유료 서비스 연결, 비밀 키 사용, 운영 데이터의 파괴적 삭제는 별도 승인 대상이다.
- 일반적인 테스트 fixture 생성·테스트 전용 DB 정리와 로컬 개발 migration은 승인된 기능 안에서 수행한다. 기존 실제 데이터 손실 가능성이 있는 작업은 먼저 결과·복구안을 준비해 확인받는다.

**중요**: 이 문서는 초안이다. 사용자가 검토 후 개발 착수를 요청하면 위 자율 진행 규칙을 적용한다. 이번 턴에서 새 기능 코드를 만들거나 현재 실연동 설정·데이터·승인 설정을 바꾸지는 않는다.

## 13. 공통 검증·완료 정의

- 기능 요구의 정상/오류/빈 상태가 웹·앱에서 동작한다.
- 실제 인증·DB 검증에서 A/B 계정이 격리된다. 인증/소유권 검사를 mock으로 대체하지 않는다.
- 외부 API와 지도는 공식 응답 계약 기반 mock으로 검증하고 테스트 중 실제 외부 호출이 없음을 확인한다.
- 동시 호출·기간 경계·DB 장애·재시작 후 한도 보존과 미설정 차단을 확인한다.
- Google 표시 데이터가 DB/영속 캐시에 남지 않고, 로그아웃 후 이전 계정 정보가 사라진다.
- 기존 기능·데이터의 회귀 테스트, lint·타입 검사·웹 빌드·앱 번들 검증을 수행한다.
- 브라우저 테스트는 실제 로컬 서버와 분리 DB에서 진행한다. 테스트가 사용자 데이터를 삭제해서는 안 된다.
- 장비가 없어 실기 검증하지 못한 경우, mock·브라우저·번들 검증과 구분해서 보고한다.
- 기능 문서·디자인·API 계약·테스트·작업 브랜치/커밋·푸시 결과가 남아야 완료다.
- ‘키 없이 구현/mock 검증 완료’는 ‘유료 API 실제 연결 완료’가 아니다. 두 상태를 별도로 보고한다.

## 14. 검토하면 좋은 항목

사용자 확인으로 확정한 내용과 남은 결정을 구분한다. 이후 사용자 승인으로 기능 개발을 시작했다. 본문의 현재 구현 비교는 착수 시점 기록이며, 최종 상태는 인수인계 문서를 기준으로 확인한다.

확인된 내용:

- 새 Google 장소 검색에 상호명·음식 종류·대표 메뉴를 반영한다.
- 저장할 때 목적·음식 종류·대표 메뉴 중 최소 한 그룹의 항목 하나 이상을 연결한다.
- 본인 계정의 아이디·비밀번호 로그인으로 시작하고 OAuth는 이후 확장 가능하게 둔다.

남은 결정:

1. 지도 핀은 현재 페이지부터 표시할지, 전체 검색 결과 표시가 필수인지.
2. 카테고리 삭제로 마지막 분류가 없어질 때 ‘다른 분류를 먼저 연결하도록 차단’하는 안전 정책을 사용할지.
3. 초기 계정 생성 수단과 아이디의 구체적인 형식은 로그인 디자인·설계 단계에서 정한다. 누구나 가입하는 공개 회원가입은 현재 범위 밖이다.

위 내용은 질문을 모두 답하기 전까지 문서를 읽지 못한다는 의미가 아니다. 사용자 피드백을 반영해 v1 확정본으로 업데이트하기 위한 결정 목록이다.
