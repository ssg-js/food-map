# 백엔드 배포 전 검토 · 2026-11-17

기준 코드: `fd9780c`에서 시작한 현재 작업 브랜치. 단일 소유자용 맛집 보관 서비스이며 공개 가입·OAuth·다중 사용자 확장은 이번 검토의 구현 범위가 아니다. 이 문서는 코드로 확인한 사실과 클라우드 운영에서 검증해야 할 조건을 구분한다. 클라우드·실제 Google 요청·사용자 DB 변경은 수행하지 않았다.

## 검토 범위와 판정 방법

`src/app/api/**`의 15개 Route Handler, `src/shared/lib/**`의 인증·카탈로그·Google 제공자/사용량 모듈, `prisma/schema.prisma`와 기존 마이그레이션, 단위·제품·DB 통합 테스트를 읽었다. Next Route Handler의 설치 버전 문서(`node_modules/next/dist/docs/01-app/03-api-reference/03-file-conventions/route.md`)를 확인했다. 스키마·인증 라이브러리·인프라를 교체하지 않았다.

심각도는 현재 개인용 서비스에서 필요한 공격 전제와 영향으로 산정했다. 아래의 '확인'은 코드와 회귀 테스트로 재현 가능한 결함을 뜻한다. '운영 조건'은 취약점이 입증된 것으로 취급하지 않는다. 이 검토가 침투 테스트나 클라우드 설정 검증을 대신하지 않는다.

## 확인된 결함과 반영한 개발 지시

### BE-01 · 중간 · 차단된 조회가 공유 검색 예산을 소진

- 이전 근거: `personal-budget.ts`는 `reserveSearchRequest(prisma, true)`를 별도 트랜잭션으로 먼저 커밋하고 나중에 개인 한도를 검사했다.
- 재현: live 모드에서 개인 일일 한도 1, 공유 일일 한도 100으로 두고 첫 요청 후 두 번째 요청을 거부한다. Google 요청은 없지만 기존 코드는 공유 사용량을 2로 기록했다. 이를 반복하면 검색이 실제 제공되기 전에 전체 한도를 소진할 수 있었다.
- 수정: `src/shared/lib/google-places/personal-budget.ts:68`에서 공유 예약을 개인 카운터와 같은 트랜잭션에 포함했다. `search-budget.ts`의 내부 예약 함수를 재사용한다. 어떤 한도라도 거부하면 모든 카운터가 롤백한다. 실제 외부 fetch 전에 예약은 커밋되고, 제공자가 오류를 반환한 요청은 환불하지 않는 보수적 정책을 유지한다.
- 검증: DB 통합 테스트에 개인 거부/공유 거부 양방향 롤백과 8개 동시 요청에서 정확히 2개만 승인되는 사례를 추가했다. 실제 DB 실행 결과는 통합 검증 문서를 참조한다.

### BE-02 · 중간 · 임의 로그인 아이디로 제한 기록 증가 및 해시 연산 반복

- 이전 근거: 로그인 API는 존재하지 않는 임의 username마다 새 `LoginAttempt` 해시 행을 만들었다. 키에는 만료 기간 정보가 없어 오래된 기록을 정리할 수 없었다. username을 바꾸면 동일한 서버에서 비밀번호 해시 검증을 반복시킬 수 있었다.
- 수정: `src/app/api/auth/login/route.ts`에서 모든 요청에 DB 기반 전역 100회/15분, 실제 credential에만 추가 10회/15분 제한을 둔다. 성공해도 전역 카운터는 유지한다. 임의 username으로 개별 DB 행을 생성하지 않는다.
- 저장/정리: `src/shared/lib/auth-attempt.ts`는 시간 구간 prefix와 scope SHA-256 해시를 사용한다. 24시간을 지난 새 형식 행을 프로세스당 최대 1시간에 한 번, 최대 100개씩 정리한다. 제한 자체는 DB atomic upsert로 모든 프로세스가 공유하며, 프로세스 메모리는 정리 빈도 조절에만 사용한다. 정리 실패가 제한을 건너뛰지 않는다.
- 기존 보안 유지: Better Auth의 없는 username에 대한 dummy password hash 경로를 유지한다. 설치된 `better-auth/dist/plugins/username/index.mjs`에서 확인했다.
- 제한/트레이드오프: 계정별 제한과 전역 제한의 수치가 다르므로 반복 공격에서 401/429 응답 차이는 남는다. 전역 한도 자체도 공격자가 먼저 채울 수 있어 가용성을 보장하지 않는다. 외부에 개방할 때는 신뢰할 수 있는 출발지 기반 edge 제한이 추가로 필요하다. 임의 `X-Forwarded-For`를 신뢰하는 우회 가능한 IP 제한은 넣지 않았다.
- 검증: 제품 테스트에서 서로 다른 미존재 아이디 3개가 한 개의 전역 행만 만들고 전역 카운터 100 이후 429가 되는지 검사한다.

### BE-03 · 중간 · JSON 본문을 검증 전 무제한으로 메모리에 읽음

- 이전 근거: 인증을 포함한 모든 POST/PATCH는 `request.json()`으로 전체 본문을 읽은 뒤 Zod로 문자열 길이를 제한했다. 청크/큰 본문은 스키마 제한에 도달하기 전에 메모리를 소비할 수 있었다. 로그인 제한도 본문 파싱 다음에 적용됐다.
- 수정: `src/shared/lib/json-body.ts:13`에 공통 스트리밍 reader를 만들고 8개 Route Handler의 POST/PATCH에 적용했다. 실제 UTF-8 바이트 64KiB와 전체 읽기 10초를 제한한다. 큰 Content-Length는 바로 거부하고, 길이가 없거나 거짓이어도 실제 바이트 수를 검사한다. 초과 413, 타임아웃 408, 잘못된 JSON/UTF-8/빈 본문 400이며 안전한 공통 오류와 no-store 응답을 보낸다. 한글 카테고리 100개 등 기존 정당한 요청 크기를 허용한다.
- 검증: 정확한 경계 크기, UTF-8 중간 청크, 길이 없는 초과, 위조된 짧은 길이, 선언 길이 초과, 잘못된 JSON, 빈 본문, 손상된 UTF-8, 정지된 스트림을 단위 테스트로 확인했다. 제품 테스트는 70KiB 로그인 본문이 인증·제한 기록 쓰기 전에 413으로 거부되는지 검사한다.
- 경계: 앱 reader에 도달하기 전 Next/프록시가 수행하는 버퍼링과 느린 TCP 연결 공격까지 이 코드가 제어하는 것은 아니다. ingress의 64KiB 제한·연결/본문 타임아웃도 배포 전 설정해야 한다.

### BE-04 · 낮음 · 개인 응답 캐시 정책 누락

- 이전 근거: 개인 조회 GET에는 no-store가 있었지만 카테고리 생성/수정 및 맛집 수정 응답, 일부 검증 오류에는 없었다. 기본 Next 동작에서 사용자 간 유출이 재현된 것은 아니며, CDN 캐시 재정의·서비스워커 도입 시 실수할 수 있는 불일치다.
- 수정: `src/shared/lib/private-response.ts:5`의 `privateJson`을 통해 `private, no-store, max-age=0`를 강제한다. 기존 쿠키와 HTTP 상태는 보존한다. 카탈로그 mutation/오류, 설정/로그인, 장소 상세, 구형 admin 진입 응답에 적용하고 204 삭제·로그아웃에도 같은 헤더를 적용했다. 검색 응답도 private를 명시한다.
- 검증: 단위 테스트에서 잘못된 public 캐시 지정을 덮고 쿠키/409를 보존하는지 확인한다. 제품 테스트에 생성 201/검증 실패 400/삭제 204의 no-store 검사를 추가했다.

### BE-05 · 낮음 · 손상된 개인 사용량 카운터가 한도를 확장

- 전제: 애플리케이션 공개 API를 통한 카운터 수정 경로는 없다. 운영자 직접 DB 수정 또는 데이터 손상이 필요하다.
- 기존 보호 구분: 공유 GoogleSearchBudget에는 기존 마이그레이션의 `budget_limits` CHECK가 있어 음수 저장을 DB에서 이미 거부한다. ApiUsage에는 음수 CHECK가 없어 별도 애플리케이션 방어가 필요했다.
- 수정: 개인 카운터가 정수·0 이상인지 확인하고 음수/손상 시 `SEARCH_BUDGET_UNCONFIGURED`로 차단한다. 공유 카운터에도 방어 검증을 추가하되 기존 DB 보호를 대체하지 않는다. 월/일 상한은 유지한다.
- 검증: 별도 DB 통합 테스트에서 공유 사용량 -1 갱신 자체가 CHECK에 거부되고 정상 값이 유지되는지 검사한다. 개인 ApiUsage는 -1 저장 후 예약이 UNCONFIGURED로 거부되고 공유 카운터를 소진하지 않는지 확인한다.

### BE-06 · 낮음 · 설정 공백 및 취소 전파

- 인증 허용 Origin 목록은 trim/filter해서 정상 HTTPS 주소 사이 공백으로 로그인이 잘못 거부되는 운영 오류를 줄였다. 프로덕션 HTTPS/비밀 검사는 배포 가드 담당 변경을 함께 적용한다.
- Google search fetch 신호에 들어온 요청의 abort 신호를 기존 10초 타임아웃과 결합했다. 검색을 취소한 뒤 서버 측 요청이 불필요하게 지속되는 시간을 줄인다. 이미 예약/전송한 과금 요청의 환불을 약속하지 않는다.

## 정상 구현으로 확인한 보호 장치

- 모든 카탈로그 API는 세션을 확인하고 소유자 범위로 조회·수정·삭제한다. `RestaurantCategory`의 복합 FK가 다른 소유자의 맛집/카테고리 연결을 DB에서도 거부한다.
- 공개 Better Auth catch-all route를 노출하지 않아 공개 회원가입·아이디 가용성 조회·임의 계정 API가 서비스로 연결되지 않는다. 최초 설정은 별도 비밀 토큰과 DB claim, 기존 계정 존재 검사가 필요하다.
- 관리자 API는 실제 로그인 계정의 OPERATOR 역할을 검사한다. 기존 관리자 키만으로 접근하는 경로는 410이다.
- 쿠키 기반 변경은 Origin 검증, 앱 API는 인증된 Bearer를 사용한다. 임의 forwarded-host를 권한 판단 근거로 신뢰하지 않는다.
- 복구 키는 고엔트로피 난수이며 DB에는 해시만 저장한다. 현재 비밀번호로 재인증해야 재발급되고, 비밀번호 재설정은 키를 일회 소비하고 모든 세션을 폐기한다. 기존 비밀번호 로그인/키 재발급과 재설정 경쟁도 트랜잭션·재검증으로 다룬다.
- 카탈로그 충돌은 updatedAt 버전과 Serializable 트랜잭션으로 검사한다. 카테고리 삭제 시 마지막 유효 분류가 없어지는 요청은 거부한다.
- 외부 장소 URL은 고정된 Google 호스트이고 ID는 인코딩한다. 리다이렉트는 금지하며 필드 마스크·레스토랑 유형·검색 범위·결과 좌표 필터를 제한한다. 외부 오류 본문·키를 사용자 오류로 그대로 반환하지 않는다.
- DB에는 Google place ID와 사용자 카테고리를 저장하고 Google 응답 내용을 영구 저장하지 않는다. 위치 좌표도 사용자 DB에 추가하지 않았다.

## 미완료 운영 조건과 PM 후속 지시

### DEP-BE-01 · 공개 배포 차단 조건 · edge 보호와 프록시 신뢰

전역 로그인 100회/15분, 복구 API 20회/15분은 소규모 개인 앱의 비용 상한을 줄이지만 공격자가 한도를 소진하면 정상 사용자가 잠시 차단된다. 공개 DNS를 열기 전 cloud WAF/방화벽에서 신뢰할 수 있는 출발지 기준 속도 제한, 연결/본문 타임아웃과 64KiB 크기 제한을 설정한다. 서버는 클라이언트가 직접 넣은 X-Forwarded-For를 기반으로 보호한다고 주장하지 않는다. 계정 잠금/실패 급증 관측을 운영 대시보드에 연결할 담당자를 지정한다.

### DEP-BE-02 · 공개 live Google 배포 차단 조건 · 과금 경계

서버 카운터는 이 서비스의 Places 검색/상세 요청만 제한한다. Maps JavaScript 로드, 다른 프로젝트/클라이언트에서 같은 키 사용, Google의 SKU/청구 정책은 제한하지 않는다. Cloud Console에서 브라우저 키 referrer/API 제한과 서버 키 제한, API/SKU quota, 청구 알림 및 현재 사용량을 실제로 확인해야 한다. 알림은 자동 비용 차단이 아니다. 월 첫 요청 전에 새 월 예산 row를 검증·준비하지 않으면 안전하게 검색이 차단되므로 매월 운영 책임자를 정한다.

### DEP-BE-03 · 운영 절차 필요 · 최초 설정 강제 종료 복구

`src/app/api/auth/setup/route.ts`의 CLAIMED 상태는 try/catch 오류에서는 복구되지만, 프로세스 강제 종료에서는 영구적으로 남을 수 있다. 실행 중인 설정을 자동 회수하면 중복 계정/권한 경쟁이 생길 수 있어 시간만으로 풀지 않았다. 배포 전에 최초 설정을 완료하고 OPERATOR 로그인/복구 키를 확인한다. 사고 시에는 외부 초기 설정 진입을 일시 막고 모든 앱 인스턴스의 설정 작업을 중지한 후 DB 백업을 만든다. 운영자는 `BootstrapState`, PENDING/OPERATOR 사용자·계정과 카테고리 소유권을 읽기 검사한다. 유효 OPERATOR가 있으면 DONE, 없고 미완성 PENDING 데이터가 확인된 경우에만 소유자 확인·백업 후 트랜잭션으로 정리/READY 회수한다. 운영 데이터에서 무조건 DELETE 또는 초기화 명령을 자동 실행하지 않는다.

### DEP-BE-04 · 운영 절차 필요 · 보존·백업·관측

새 형식 LoginAttempt는 자동 정리하지만 이전 무기한 해시 형식 기록은 기간을 알 수 없어 자동 삭제하지 않는다. 배포 후 이전 버전 인스턴스가 모두 사라지고 15분 경과한 유지보수 시간에 백업/확인 후 이전 형식만 정리할 수 있다. Session/Verification 만료 행, 오래된 ApiUsage/MonitoringSnapshot 등 보존 기간과 백업·복구 목표를 결정한다. 현재 코드만으로 백업 복원 성공·권한 최소화·DB TLS·클라우드 연결 풀을 확인할 수 없다. 공개 배포 전 실제 복원 연습과 DB 사용자 권한 검증을 완료한다.

### DEP-BE-05 · 서버리스 환경 검증 · Monitoring 실행 시간

## 미사용·중복 코드 판정

검사 방법은 `rg`로 `src`, `apps`, `packages`, `scripts`, `tests`의 실제 import/call을 추적했다. 파일 존재만으로 런타임 낭비라고 판단하지 않았다.

- `src/shared/lib/operator-access.ts:2`의 `requireOperator`는 정의 외 호출/수입이 없다. 현재 관리자 API는 `admin-access.ts`의 `isAdmin`을 사용한다. 제거 가능한 소스 유지보수 후보지만 현재 앱이 두 인증 가드를 중복 실행한다는 증거는 없다.
- `src/shared/lib/catalog.ts:36`의 `apiError`는 정의 외 호출이 없다. 같은 파일의 `catalogSelect`, `flattenRestaurant`, `listCatalog`, 카테고리 스키마는 개인 카탈로그 API에서 사용하므로 파일 전체를 삭제하면 서비스가 깨진다. 사용하지 않는 오류 변환 export만 추후 정리할 수 있다.
- `src/shared/lib/admin-auth.ts`의 `ADMIN_COOKIE`, `adminKey`, `signAdminSession`, `validAdminSession`은 현재 서버 라우트가 쓰지 않는 이전 관리자 키/쿠키 방식이다. 세션 함수는 `tests/unit/admin-auth.test.ts`에서만 호출된다. 반면 같은 파일의 `sameOrigin`은 현재 로그인·설정·복구·개인 변경·관리자 Monitoring에 쓰이므로 유지해야 한다. 구형 기능과 테스트를 함께 별도 정리하고 Origin 검증은 남기는 작은 후속 작업이 적절하다.
- 확인 시점 기존 Next 산출물의 서버 JavaScript에서 `food-map-admin`/`signAdminSession`/`validAdminSession` 문자열이 검색되지 않았다. 새 최종 빌드의 압축·tree-shaking 결과와 번들 크기를 정밀 측정한 것은 아니지만, 현재 검토로는 사용자에게 전달되는 중복 인증 코드 비용을 주장할 수 없다. 명확한 비용은 소스·문서·테스트 유지보수 혼란이다.
- `src/shared/lib/api-error.ts`는 구형 `src/features/place-registration/api/*`에서 수입한다. 해당 API들은 구형 등록 hooks로 연결되지만 현재 공유 registration 컨트롤러와 별개다. 프론트 담당의 entry reachability 검토와 함께 제거 여부를 정해야 한다. 이름만 보고 전체 삭제하지 않았다.
- 중복 privateHeaders 정의는 이번 수정에서 `private-response.ts`로 모으고 기존 import 경로는 재수출하여 계약을 유지했다. 실제 중복 동작과 불필요한 대규모 리팩터링을 동시에 피했다.

코드 삭제를 자동으로 대량 수행하지 않았으며, 현재 기능·테스트를 통과한 독립 수정 후 구형 묶음을 작은 단위로 정리하는 것을 PM 후속으로 남긴다.
